## 60틱 이동 보정 — 측정 결과 (2차, 실제 시간 기준)

**1차 측정은 틀렸습니다.** "틱 수" 기준으로 재서, 60틱에서 플레이어가 실제로 1/3 속도로 느려진 것을 잡지 못했습니다 (직접 플레이로 발견).

원인: 바닐라 **클라이언트는 서버 틱레이트를 올려도 1초에 20틱보다 빨리 돌지 않습니다**
(`Minecraft.getTickTargetMillis` = `max(50ms, 서버 1틱)`). 플레이어 이동은 클라이언트가 계산하므로 원래 20틱 속도 그대로인데,
60틱용 보정을 걸어 1/3 로 느려졌던 것입니다.

고침: 이동 보정(`MovementScale`)은 **서버가 직접 움직이는 생명체(더미 · 몹)에만** 겁니다. 플레이어는 보정하지 않습니다 (공중 가속 Mixin 도 삭제).

| 항목 | 서버 20틱 | 서버 60틱 |
|---|---|---|
| 클라이언트 실제 틱 | 20틱/초 | 20틱/초 |
| 플레이어 걷기 (실제 시간) | 4.18칸/초 | 4.19칸/초 |
| 주민 20칸 낙하 (서버 틱 ÷ 틱레이트) | 1.250초 | 1.250초 |

클라이언트 게임테스트는 통합 서버를 클라이언트 틱에 묶어 실제로는 1초 20틱만 돌리므로, 서버 쪽 값은 게임 속 시간으로 쟀습니다 (실제 서버는 설정대로 돎).

### 중요한 결과 — 60틱이 판정에 주는 이득의 한계
- 바닐라 클라이언트는 **자기 위치를 1초 20번**만 서버에 보냅니다. 서버가 60틱이어도 **플레이어를 맞히는 판정은 여전히 20Hz 위치**로 합니다.
- 60틱이 확실히 나아지는 것: 서버 쪽 스킬 타이밍(쿨타임 · 지속 · 투사체 · 돌진 · 더미/몹 움직임)이 17ms 단위로 세밀해짐.
- 플레이어 대 플레이어 판정까지 60Hz 로 하려면 **클라이언트도 60틱**으로 돌려야 합니다 (`getTickTargetMillis` Mixin) → 클라이언트 입력 · 애니메이션 · 모드 클라이언트 코드 전부 3배, 이동 보정도 플레이어에게 다시 필요, 위치 패킷 3배.
- 대안: 서버 20틱 유지 + 입력 서브틱 타임스탬프 + 지연 보상(되감기)으로 판정 정확도를 올리는 방법.

## 1단계 구현 (서버 60틱 + 되감기 + 서브틱)

| 부분 | 내용 |
|---|---|
| 게임 틱 시계 `core/tick/GameClock` | 서버는 60틱으로 돌지만 직업 스킬 · CC · 쿨타임 · 게이지 · HUD 는 1초 20번(게임 틱)에만 돎 → 60틱에서도 스킬 시간 · 거리가 그대로. 입력 창 · 조준 유효 시간도 게임 틱 기준. 바닐라 무적 시간(invulnerableTime)도 게임 틱 기준으로 붙잡음 |
| 서버가 움직이는 생명체 | `Motion` 의 밀기 · 돌진 속도를 서버 틱레이트로 나눔 (플레이어는 클라이언트 20틱이 적용하므로 그대로) · `MovementScale` 로 마찰 · 중력 보정 |
| 되감기 판정 `combat/HitboxRewind` | 플레이어 히트박스를 서버 틱마다 기록 (60개 링버퍼). `Hitscan` 이 쏜 사람의 핑 + 50ms (최대 200ms) 만큼 되감아 판정 · 머리 판정도 되감은 눈높이로. 몹 · 더미는 지금 위치 |
| 서브틱 입력 `net/SkillInputPayload` · `input/InputTiming` · `client/input/InputTimingTracker` | 클라이언트가 프레임마다 5개 키 눌림을 보고 바뀐 순간의 "틱 안 %" 를 보냄. 서버는 0~1 로 자르고 없는 슬롯 · NaN 버림 · 1초 60개 넘으면 버림 · `pressedAt` · `heldTicks` 로 소수 시각 제공 (쓰는 스킬은 아직 없음) |
| 시험 | `NetcodeTest` (시간 문자열 · 되감으면 맞고 안 되감으면 빗나감 · 서브틱 자르기 · 과다 입력 버림), `TickRateClientTest` 에 "기절 2초가 60틱에서도 2초" 추가. (2단계에서 모든 시험을 60틱으로 옮김) |

60틱 측정: 걷기 4.18칸/초(20틱 4.20) · 주민 20칸 낙하 1.250초(같음) · 기절 2.000초(같음).

**한계**: 게임 로직은 아직 50ms 단위입니다. 60틱의 이득은 입력이 17ms 안에 처리되는 것과 되감기 기록이 촘촘한 것뿐 — 플레이어 위치는 클라이언트가 1초 20번 보내므로 되감기도 그 단위입니다.
2단계(클라이언트 60틱)에서 스킬을 초 단위로 옮기고 게임 틱 시계를 없앱니다.

## MSPT

한 플레이 서버(클라이언트와 같은 컴퓨터), 60틱 설정, 봇이 쉬지 않고 평타 · 스킬 · 궁극기 사용. 값은 **틱 하나 처리 시간**이라 시험 환경이 실제로 몇 틱을 돌렸는지와 상관없이 유효합니다:

| 봇 | MSPT | 60틱 예산 16.67ms 대비 |
|---|---|---|
| 0 | 0.37ms | 2% |
| 10 | 0.89ms | 5% |
| 20 | 1.89ms | 11% |

봇은 서버 전투 로직 부하만 냅니다 — 실제 접속자의 이동 패킷 · 청크 전송 · 파티클 패킷 전송은 빠져 있습니다.
최종 확인은 **실제 클라이언트 10개**로 해야 합니다 (아래 측정 방법).

## 검토 요청에 대한 답

### 26.2 → 26.3
- Fabric 26.3 지원은 2026-09-15 공개 (Fabric API 0.154.0+26.3, Loom 1.17, Loader 0.19.5 — 지금과 같은 도구).
- 변경 요약에 AttachmentChange 마무리 · 엔티티 기본 속성 이벤트 변경 · 바닐라 리팩터로 인한 일부 API 제거가 있습니다. 네트워킹 · 틱레이트의 큰 변경은 요약에 없음.
- 모드는 틱레이트를 바닐라 공개 메서드(`MinecraftServer.tickRateManager().setTickRate`)와 속성(`friction_modifier` · `air_drag_modifier`)만으로 다뤄 새 Mixin 이 없어서, 26.3 이전 부담은 기존 Mixin(렌더러 쪽)이 대부분입니다. **실제 이전 전에는 26.3 으로 빌드해서 깨지는 곳을 확인해야 합니다** (아직 안 해 봄).

### 틱레이트 API (26.2 에서 확인)
- 설정: `server.tickRateManager().setTickRate(60f)` — `/tick rate` 명령과 같은 경로.
- 클라이언트 동기화: 틱레이트 값은 자동으로 전달됨 (`ClientboundTickingStatePacket`, 접속할 때도). **하지만 클라이언트 자신은 20틱보다 빨리 돌지 않음** — 위 "중요한 결과" 참고.
- 되돌림: 매 틱 목표와 다르면 다시 설정 (`/tick sprint` · `freeze` 중에는 두지 않음).
- 바닐라 타이머 3배 회피: `lockGameRules` 가 켜져 있으면 `advance_time` · `advance_weather` · `spawn_mobs` · `spawn_monsters` false, `random_tick_speed` 0, `natural_health_regeneration` false.
  바닐라 포션 · 불 붙음 · 아이템 사라짐 · 허기는 여전히 3배 — 게임에서 쓰지 않거나 직접 관리해야 합니다.

### 상태 저장
- 쿨타임 · CC · 스택은 지금도 서버 메모리(`PlayerProfile` · `Combatant`)이고 Attachment 로 동기화하지 않습니다. **쿨타임을 Attachment 로 옮기지 않았습니다.**
- 지금 HUD 는 서버가 바뀔 때만 보내는 방식(`HudPayload`)이지만, 문서가 원하는 "끝나는 틱 한 번 → 클라이언트가 셈" 은 아직 아닙니다 → 다음 단계.

### 핫리로드로 체력 상한이 바뀔 때 (제안)
- 최대 체력 속성을 새 값으로 바꾸고, **체력 비율을 유지** (최대 300 에 150 이었으면 최대 200 에서 100). 줄어들 때 바닐라는 넘친 체력을 잘라 버리므로 비율로 먼저 계산한 뒤 설정.
- 이동속도는 속성 수정자만 바꾸면 바로 반영. 경기 중이면 "다음 라운드부터" 적용하는 선택지도 둠.

### 예측 롤백 완화 (제안)
- 쿨타임 바: 예측으로 시작하되 서버 확인 전 0.1초 동안은 "대기" 색으로, 거부되면 되돌리는 대신 빠르게 채워 원래 상태로(깜빡이지 않게).
- 애니메이션: 거부 시 즉시 끊지 말고 3~4틱에 걸쳐 원래 자세로 섞음. 거부율 자체를 줄이기 위해 클라이언트도 쿨타임 · 봉인을 알고 있을 때만 예측.

### HitboxRewind 메모리
- 스냅샷 하나 = 박스 6 double(48바이트) + 틱 번호. 기본 배열(`double[60 × 6]`) 링버퍼면 플레이어당 약 3KB, **10명 약 30KB** — 무시할 수준.
- 객체로 저장하면 60개 × 약 64바이트로 플레이어당 약 4KB. 어느 쪽이든 부담 없음.

### MSPT 측정 · 10인 부하
- 서버: `/overbreak mspt` (바닐라 평균 틱 시간), `/tick query`, 자세히는 spark 프로파일러 모드.
- 서버 로직 부하: `/overbreak bots <n>` (이번 결과).
- 실제 10인: 전용 서버 + 클라이언트 10개. 한 컴퓨터에서 무리면 Fabric 클라이언트 게임테스트의 전용 서버 연결 기능으로 여러 클라이언트를 띄우거나, 여러 사람이 접속한 상태에서 spark 로 측정.

### 폐기 목록
- 모드 안에는 `.mcfunction` · 스코어보드 · 아이템 내구도 쿨타임 막대 · 좌클릭 우회가 원래 없습니다 (모드는 처음부터 직접 입력 · HUD).
- `×10 / ×100 정수 피해` 는 모드에 남아 있습니다 (`SkillDamage.deal` / `dealFine`) → 직업을 초 단위로 옮길 때 float 로 함께 바꿀 대상.
- 보존할 설계 자산: 데이터팩 `README.md` · `SYSTEM.md` 의 직업별 수치표와 상호작용 노트, 모드 `docs/PORTING.md` — JSON 이관 때 원본으로 씀. 실서버 폴더에서 지우지 않았습니다.

## 2단계 — 클라이언트까지 60틱, 20틱 폐기

**결정: OVERBREAK 는 1초 60틱 고정.** 20틱으로 돌리는 경로 · 설정 · 시험은 두지 않습니다.

- 클라이언트도 60틱 (`MinecraftTickRateMixin`, 실측 59~60틱/초). 파티클 수명은 20틱 속도 유지 (`ParticleEngineMixin`).
- 직업 코드의 숫자는 **1/20초 단위 시간**으로 그대로 두고, 틱에 넣는 순간 `Ticks` 로 바꿈: `of`(시간→틱) · `speed`(시간당→틱당) · `every`(주기) · `time`(틱→연속 시간) · `ambient`(매 틱 뿌리던 파티클은 1/20초마다만).
- 7직업 · 게임 흐름 · CC · 돌진 · 쿨타임 · HUD · 디스플레이 보간 · 제목 표시 시간 모두 변환. `GameLoop` 는 매 서버 틱 전부 돎.
- 클라이언트 연출은 `ClientClock`(연속 시간) 기준 — 애니메이션 키프레임 수치는 그대로.
- 바닐라 물리 보정 추가: 넉백 (`LivingEntityKnockbackMixin`, 맞고 3배 날아가 낙하 피해 나던 문제), 공중 부양 (`LivingEntityLevitationMixin`, 에어본을 다시 바닐라 부양으로), 최소 속도 0.003 문턱 (`LivingEntityMinVelocityMixin`, 느린 상승이 잘려 멈추던 문제), 느린 낙하 (`LivingEntitySlowFallMixin`).
- 시험: 시간은 1/20초 단위로 적고 `T.of` 로 틱 변환. 서버 게임테스트 67개 통과, 직업 클라이언트 시험 9개 통과, `TickRateClientTest` 는 원래 조작감 기준값과 비교:

| 항목 | 기준 (원래 조작감) | 60틱 |
|---|---|---|
| 걷기 | 4.19 칸/초 | 4.16 |
| 점프 | 1.252 칸 | 1.252 |
| 주민 20칸 낙하 | 1.250 초 | 1.250 |
| 기절 2초 | 2.000 초 | 2.000 |
| 에어본 0.8초 | 0.565 칸 | 0.560 |
| 넉백 거리 · 높이 | 1.989 · 0.965 칸 | 1.990 · 0.941 |
